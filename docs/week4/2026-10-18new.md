## Why I did this next

In Week 3, my linear regression and random forest were able to fit parts of a
recorded path, but they did not actually predict the next movement. This is
because they treated every sample as a separate row, meaning that they had no
memory of what came before. Additionally, the R² numbers near 1.0 were scored
on the training data. As a result, they measured how well the model could
reconstruct the path, not how well it could predict it.

Before using a bigger model, I wanted to check whether a neural network even
matches the problem I actually have. So, my question for this week was:

> Can a model use a short history of mouse movement to predict the next
> displacement better than a simple constant-velocity prediction?

## The answer: yes, and it holds across splits

The table below shows the held-out error 20 ms ahead, averaged over 3
different session-level splits. Every number is from recordings that the
model never trained on.

| model | params | mean px | (min–max over seeds) | median px | win% vs const-vel | seeds beating const-vel |
|-------|--------|---------|----------------------|-----------|-------------------|--------------------------|
| gru | 3618 | **5.36** | 4.69–6.10 | **2.02** | 55% | **3/3** |
| lstm | 4802 | 5.65 | 4.74–6.50 | 2.15 | 52% | **3/3** |
| mlp_res | 8194 | 6.14 | 5.15–7.14 | 2.79 | 40% | **3/3** |
| constant velocity | 0 | 7.02 | — | 2.28 | — | — |
| no movement | 0 | 16.89 | — | 7.48 | — | — |

Using a window of recent motion beats constant velocity by about 24% on mean
error, and this was true on every split I tried. The recurrent models also
beat constant velocity on median error. This is important, since a model can
win on mean error by only being better on a few large movements. Winning on
the median means that the model is better on the typical movement as well.

## Part 5 — How a sequence model uses history

Tensor shapes, recorded as planned:

```
input  X : (batch, window=20, channels=3)
target Y : (batch, 2)
```

**One change from my plan.** Originally, I had written the input as
`[dx, dy, vx, vy]`. However, this is redundant. After resampling to a fixed
time step, `vx = dx/dt` where `dt` is constant. This means that `vx, vy` are
just a scaled copy of `dx, dy`, so they do not give any new information. As a
result, I replaced the extra pair with something that the model cannot figure
out from the deltas: the session's native polling rate, as
`log2(native_dt / step_ms)`. A negative value means that the recording was
sampled finer than the grid, meaning that real detail got downsampled. A
positive value means that it was sampled coarser, meaning that detail got
interpolated in. I tested this on the 23-session dataset, before the motion
filter existed. With the channel, mean error was 7.71 px, and without it,
mean error was 8.19 px. Thus, the channel is worth keeping.

**Does memory or complexity cause the improvement?** This was the part of the
plan I most wanted an answer to. Testing a windowed linear model and an MLP
alongside the recurrent models answered it. The results on one split at
batch 64 are below:

| model | mean px | median px | win% vs const-vel |
|-------|---------|-----------|-------------------|
| lstm | 5.86 | 1.85 | 62% |
| mlp_res | 6.29 | 2.06 | 60% |
| gru | 6.45 | 2.35 | 47% |
| mlp (no recurrence) | 6.53 | 2.51 | 42% |
| cnn | 7.05 | 2.84 | 37% |
| gru_res | 7.57 | 2.98 | 36% |
| linear on window | 9.56 | 3.52 | 34% |
| constant velocity | 7.71 | 2.32 | — |

The plain MLP nearly matched the GRU (6.53 vs 6.45), even though it has no
recurrence at all. This means that most of the improvement comes from having
the whole window available, not from the model keeping a sequential state.
As a result, recurrence only adds a smaller extra margin than I expected.

The windowed linear model is the useful floor. Constant velocity is itself a
linear function of the last delta, so a linear layer over the window can
represent the baseline exactly. However, it scored 9.56 px, which is worse
than the 7.71 px baseline. This means that the least-squares optimum over
this data is not constant velocity. Thus, every model above that line is
learning real structure.

I also tried a residual framing, where the model predicts the correction to
constant velocity instead of the motion itself. This helped the MLP
(6.53 → 6.29), but hurt the GRU (6.45 → 7.57). As a result, it is not the free
win that I assumed it would be.

## Key findings

### 1. The dataset and the target decided the outcome, not the model size

This is the main thing I learned, and it matches the plan I wrote for myself:
start small, and if it does not beat the baseline, check the dataset and the
target before making the network larger. Changing the architecture on
identical data only moved mean error by about 9%. In contrast, a model lost
to constant velocity three times, and every time, the cause was the data or
the framing:

1. **Striding by row index across mixed polling rates.** My recordings are
   not all one rate. The early logs are ~1000 Hz, while the collector
   sessions are ~40–160 Hz. As a result, a 20-sample window meant 20 ms in one
   session and 240 ms in another. This means that the model was being asked a
   different question for each session. Resampling onto a fixed time grid
   fixed this. I checked it by comparing native speed (`|Δ|/dt` per event)
   against resampled speed (`|Δ|/4 ms`). The median mismatch was 13%, and it
   was similar for both regimes (12.1% below 200 Hz, 16.7% above 500 Hz).
   Thus, there is no bias depending on the rate.
2. **Interpolating across pauses.** pynput only fires while the pointer is
   moving, so holding still leaves a gap in time. Resampling across that gap
   creates smooth motion that was never actually recorded. As a result,
   windows that span a gap longer than 50 ms are now dropped.
3. **Motionless data.** After the collector produced thousands of files, 54%
   of sessions with at least 200 rows had a total path length under 50 px,
   meaning that the cursor was just sitting still. Because of this, the
   "predict zero" baseline reached a **median error of 0.00 px**. This means
   that the metric could not tell a good model from a bad one. In fact, the
   model that looked like it was winning was actually worse than doing
   nothing on most of the windows. Filtering by actual motion (instead of row
   count) is what finally let a model win honestly.

### 2. Architecture differences are small and the ranking is not stable

At batch 64, the LSTM was best (5.86 vs GRU 6.45). However, at batch 512, the
order reversed (GRU 5.36 vs LSTM 5.65). Additionally, their ranges across
seeds overlap a lot (4.69–6.10 against 4.74–6.50). This means that the GRU
and LSTM cannot be told apart on this data. What is reliable is that both
beat constant velocity on 3/3 splits. Thus, I should not report a winner
between them.

Larger batches also cost accuracy when the number of epochs is fixed. The
same LSTM went from 5.86 px at batch 64 to 6.50 px at batch 512 on the same
split. This is because there are 8× fewer gradient updates per epoch.

### 3. Two bugs that only appeared at scale

- **Timestamps.** `str(datetime.now())` leaves out the fractional part when
  the microseconds are exactly zero. As a result, one row in a long log reads
  `2026-10-18 06:11:50`, while the rest have microseconds. pandas guesses the
  format from the first row, and then raises an error when it reaches that
  row. At 13k rows, this never showed up, but at 2M rows, it is certain to
  happen. The logger now formats the timestamp explicitly, and the reader
  parses ISO8601.
- **Velocity measured across a pause.** The first row written after holding
  still had a delta that spanned the whole pause, which is a fake velocity.
  In a test with 400 ms rests, it produced a 444.6 px step in one 2 ms
  sample. The logger now splits a recording into segments at pauses
  (`idle_ms`). This removes the cross-pause delta, and also means that each
  saved file is one stretch of continuous motion.
